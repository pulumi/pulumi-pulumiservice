# Contributing to Pulumi Service Provider

First, thanks for contributing to Pulumi Service Provider and helping make it better. We appreciate the help!
This repository is one of many across the Pulumi ecosystem and we welcome contributions to them all.

## Code of Conduct

Please make sure to read and observe our [Contributor Code of Conduct](./CODE-OF-CONDUCT.md).

## Communications

You are welcome to join the [Pulumi Community Slack](https://slack.pulumi.com/) for questions and a community of like-minded folks.
We discuss features and file bugs on GitHub via [Issues](https://github.com/pulumi/pulumi-pulumiservice/issues) as well as [Discussions](https://github.com/pulumi/pulumi-pulumiservice/discussions).

### Issues

Feel free to pick up any existing issue that looks interesting to you or fix a bug you stumble across while using Pulumi Service Provider. No matter the size, we welcome all improvements.

### Feature Work

For larger features, we'd appreciate it if you open a [new issue](https://github.com/pulumi/pulumi-pulumiservice/issues/new) before investing a lot of time so we can discuss the feature together.
Please also be sure to browse [current issues](https://github.com/pulumi/pulumi-pulumiservice/issues) to make sure your issue is unique, to lighten the triage burden on our maintainers.
Finally, please limit your pull requests to contain only one feature at a time. Separating feature work into individual pull requests helps speed up code review and reduces the barrier to merge.

## Developing

Here's a quick list of helpful make commands:

1. `make ensure`, which restores/installs any build dependencies
1. `make build`, which generates models from provider's `schema.json`, builds the provider and builds all SDKs into the `sdk` folder
1. `make install`, which installs Pulumi Service Provider

## Testing

Ideally, every change should include unit tests, and every new resource a matching example in the `examples` folder.

You should also test changes manually using a Pulumi program that uses the updated SDKs. Here are some language-specific hints:

### Shared test org

Every CI test suite (`test`, the acceptance tests and the `api` tests), on every PR, creates real resources in one org: `service-provider-test-org` on `https://api.pulumi-staging.io`. Runs from different PRs overlap, so tests must not assume they have the org to themselves:

- Give every resource a name with a random suffix (`generateRandomFiveDigits()` in `examples/examples_utils_test.go`), so concurrent runs and resources leaked by failed runs can't collide.
- Avoid org-wide singletons. For example, an OIDC issuer URL can be registered only once per org, so two runs that both register `https://api.pulumi.com/oidc` conflict.

The `api` test suite starts with a sweeper (`examples/sweep_api_test.go`) that deletes resources leaked by earlier runs. It deletes a resource only if all of these hold:

- Its name, or for an environment its project, starts with one of the test prefixes in `shouldSweep`, such as `api-`, `test-` or `org-webhook-`.
- It was last modified more than 3 hours ago (`sweepMinAge`), longer than any test run, so it can't belong to a run still in progress.
- Its type's list endpoint returns a timestamp: OIDC issuers, roles, ESC environments, agent pools and organization tokens.

Webhooks, teams, policy groups and template sources have no timestamp, so the sweeper deletes them only when `PULUMITEST_SWEEP_UNDATED=1` is set, regardless of age. Use it for manual cleanup only, when nothing else is running against the org. Set `PULUMITEST_SKIP_SWEEP=1` to skip the sweeper entirely.

The sweeper targets `PULUMI_TEST_OWNER`. If you run `go test -tags api` locally against your own org, it deletes anything there whose name matches a test prefix, including resources you made by hand. Set `PULUMITEST_SKIP_SWEEP=1` if that org has anything you want to keep.

## Submitting a Pull Request

For contributors we use the [standard fork based workflow](https://gist.github.com/Chaser324/ce0505fbed06b947d962): Fork this repository, create a topic branch, and when ready, open a pull request from your fork.

We require a changelog entry for pretty much all PRs. `CHANGELOG.md` is generated by [changie](https://changie.dev), so don't edit it directly. Instead, run `make changelog` (or `changie new`) and commit the file it writes to `.changes/unreleased/`. It asks for the kind of change, a description written for users, and an optional issue or PR number to link. In rare cases where your PR is a minor change, like formatting or a typo fix, apply `impact/no-changelog-required` label to your PR instead.

changie is pinned in `mise.toml`, so `mise install` installs it.

### Pulumi employees

Pulumi employees have write access to Pulumi repositories and should push directly to branches rather than forking the repository. Tests can run directly without approval for PRs based on branches rather than forks.

Please ensure that you nest your branches under a unique identifier such as your name (e.g. `pulumipus/cool_feature`).

## Releasing

This section is for Pulumi employees only.

A release is a PR that moves the unreleased changelog fragments under a version heading. Merging it tags the release, and GitHub Actions does the rest.

1. Pick the version. `changie batch auto --dry-run` shows the version the fragments imply: a minor bump for improvements or breaking changes, a patch bump for bug fixes only. Breaking changes ship in minor releases, because a major version would need a new Go module path.
2. On a branch from `main`, run `changie batch vX.Y.Z && changie merge`. This writes `.changes/vX.Y.Z.md`, deletes the fragments, and regenerates `CHANGELOG.md`. Commit the result.
3. Open a PR with the `auto-release` label and a `Release-Version: vX.Y.Z` marker anywhere in its body. Markdown emphasis is stripped before matching, so `**Release-Version: v1.2.3**` works. The `changelog / release-pr` check fails unless the marker matches the batched version and `.changes/unreleased/` is empty.
4. Wait for the required `Sentinel` check from `run-acceptance-tests.yml`, then merge.
5. After the merge:
   - [`pulumiservice-tag-api-release.yml`](./.github/workflows/pulumiservice-tag-api-release.yml) pushes the tag `vX.Y.Z` from a GitHub App installation token. The tag push triggers `release.yml`, which builds, tests and publishes to all package managers.
   - Its `finalize` job waits for the GitHub release, marks it `--latest`, and dispatches a docs rebuild to `pulumi/registry`.
   - [`pulumiservice-release-notes.yml`](./.github/workflows/pulumiservice-release-notes.yml) adds `.changes/vX.Y.Z.md` to the top of the GitHub release body, above the schema summary and the generated list of PRs. If it didn't run, start it by hand with the version as input.
6. Check that the version is on the [Releases](https://github.com/pulumi/pulumi-pulumiservice/releases) page, marked latest, with its changelog at the top.

For a prerelease, skip steps 1 and 2 and use a `Release-Version: vX.Y.Z-alpha.N` marker. The fragments stay unreleased until the next stable release. `prerelease.yml` publishes the packages but creates no GitHub release.

Release from a PR rather than by pushing a tag or posting in #release-ops. Those skip the changelog checks and the `finalize` job, so the release isn't marked latest and the registry docs aren't rebuilt.

`run-acceptance-tests.yml` skips PRs that change only `CHANGELOG.md`, and then the required `Sentinel` check never reports. A release PR also changes files under `.changes/`, so it isn't skipped. Commenting `/run-acceptance-tests` doesn't help on a skipped PR: a comment-triggered run writes `Sentinel` to the tip of `main` instead of the PR's commit.

### API surface releases

`pulumiservice:api:*` resources are generated from the Pulumi Cloud OpenAPI spec. Running the [`refresh-api-spec`](./.github/workflows/pulumiservice-refresh-api-spec.yml) workflow with a version opens a PR that regenerates them, already labeled `auto-release` with the `Release-Version:` marker. Before merging it, add fragments for the user-visible changes on its branch, then do step 2 of [Releasing](#releasing) for that version. Re-running the workflow force-pushes the branch, so do this after the last run.
